# Size limits: which unit to use

Every size limit in this server is in one of three units: tokens, bytes or characters. Pick the unit by what the limit protects, not by what is easiest to count.

| The limit protects                                                                                           | Unit           | Why                                                                                                                                                                                                |
| ------------------------------------------------------------------------------------------------------------ | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The model's context: tool definitions, tool results, anything an agent reads                                 | **Tokens**     | Tokens are what the agent pays for and what clients cap: Claude Code moves a tool result over 25,000 tokens, or a text result over 50,000 characters regardless of token count, out of the conversation into a file the agent can read back if it needs the content. |
| Transport or memory: request bodies, raw stream reads                                                        | **Bytes**      | Networks and buffers are sized in bytes.                                                                                                                                                           |
| Text a person or agent writes that the server stores or forwards: feedback, search queries, analytics values | **Characters** | The writer reads the limit as a length ("500 characters"), and an error can say so in those terms.                                                                                                 |

Name every new size constant with its unit as a suffix: `_TOKENS`, `_BYTES` or `_CHARS`.

## Tokens

Count tokens with `@anthropic-ai/tokenizer` (a devDependency). Its counts are approximate for current Claude models, and other model families tokenize differently, so a token limit guards against growth rather than predicting exact billing. Keep about 10% headroom under any hard client limit.

The tokenizer is a test-time tool. It is not shipped in the server, so a token limit is enforced either:

1. **In a test**, when the size is fixed at build time: tool definitions and argument descriptions (`tests/specgen-gates.test.ts`).
2. **At runtime, in UTF-8 bytes**, when the size depends on live data such as logs. A byte-level BPE token always covers at least one byte, so a text of N bytes is at most N tokens. A byte cap is therefore a hard upper bound on tokens, whatever the language or symbols. Typical English JSON runs about 4.3 bytes per token (the generated tool surface: 121,423 B, 28,036 tokens), so the bound costs headroom on plain text and never overruns. One exception: the tokenizer applies NFKC first, which expands compatibility characters such as `ﷺ` (U+FDFA, 3 raw bytes) into many letters (33 normalized bytes, 15 tokens) — so the bound holds over NFKC-normalized bytes, not raw input bytes. Ordinary text in any script has none. `@anthropic-ai/tokenizer` is also a legacy approximation: Anthropic's own README says it is no longer accurate for Claude 3 and later models, so treat its counts as a guide, not an exact bound — which is also why the 10% headroom above matters.

Never use characters to stand in for tokens. Measured on log snapshots, one character ranged from 0.42 to 2.14 tokens: a 32,000-character snapshot was 13,361 tokens of emoji progress bars and 68,548 tokens of rare CJK characters.

Add a row when you add a limit.

Tool results are compact JSON unless `MCP_PRETTY_RESPONSES=true` (`src/specgen/serialize.ts`). The page budget and the log snapshot cap both measure a result in the format sent, in bytes, so compact JSON holds more rows or more log lines under the same cap instead of costing fewer tokens.

## Follow-ups

Log tools (`stream-pod-logs`, `stream-worker-logs`):

1. Page with a cursor built from the API's event id (`Last-Event-ID`, a timestamp plus a sequence number), returned as `pagination.nextCursor` like every other list. Today an agent pages by hand, passing the last container line's `ts` as `since`, which can skip lines that share a timestamp and never replays system lines. Do not page by skipping a number of lines, characters or tokens: the API cannot skip, and a live log grows and rotates between calls, so an offset points at different lines each time.
